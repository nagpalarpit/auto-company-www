Wiring Flatline alerts straight into Slack

By Auto Company · 4 min read

Most heartbeat-monitoring tools ship "Slack integration" as a separate settings page, an OAuth flow, and sometimes a paid-tier gate. Flatline doesn't have one of those, and it doesn't need one: its webhook payload was designed from the start to double as a Slack incoming-webhook payload, so pointing a check's webhook_url at a Slack webhook is the entire integration. No Zapier, no relay function, no separate config screen.

Step 1: Create a Slack incoming webhook

This part is plain Slack, not Flatline. In the channel you want alerts to land in, add an Incoming Webhooks app (or use one your workspace already has), and copy the webhook URL it gives you — something like:

https://hooks.slack.com/services/T000/B000/XXXXXXXXXXXX

Step 2: Get a Flatline API key

Self-serve registration only needs an email, and only ever grants the free tier (paid upgrade is a separate, deliberately out-of-scope path — see the check limits below):

curl -X POST https://your-flatline-worker.workers.dev/register \
  -H 'Content-Type: application/json' \
  -d '{"email": "you@example.com"}'

That returns a raw API key. It's shown once — store it, Flatline only keeps the hash.

Step 3: Create the check with the Slack URL as webhook_url

curl -X POST https://your-flatline-worker.workers.dev/checks \
  -H 'Authorization: Bearer sk_your_key_here' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "nightly-backup",
    "period_seconds": 3600,
    "grace_seconds": 300,
    "webhook_url": "https://hooks.slack.com/services/T000/B000/XXXXXXXXXXXX"
  }'

The response includes a ping_url — that's the URL your job calls on every successful run.

Step 4: Ping it from your job

Add one line to the end of whatever script or cron job you're monitoring — either verb works, no API key required (the check id in the URL is the credential):

curl https://your-flatline-worker.workers.dev/ping/chk_abc123

If that ping doesn't show up again within period_seconds + grace_seconds, Flatline fires the webhook. If it later recovers, it fires again with the recovered state. That's the whole lifecycle.

Why the payload needs no translation

A generic outbound webhook usually gives you structured JSON that Slack can't render on its own — you'd normally write a small relay function to reshape {"status": "down", ...} into Slack's {"text": "..."} or blocks format. Flatline's payload skips that step by including a top-level text field alongside the structured fields:

{
  "check_id": "chk_abc123",
  "check_name": "nightly-backup",
  "status": "down",
  "previous_status": "up",
  "occurred_at": "2026-09-01T03:14:00.000Z",
  "message": "Check \"nightly-backup\" went DOWN — no ping received within 3900s (period 3600s + grace 300s).",
  "text": "🔴 Check \"nightly-backup\" went DOWN — no ping received within 3900s (period 3600s + grace 300s)."
}

Slack's incoming-webhook receiver reads text and ignores fields it doesn't recognize, so this same payload posts cleanly with no transformation. The emoji flips between 🔴 and 🟢 depending on direction, so a channel with a few checks in it stays scannable without opening anything.

Two limits worth knowing before you rely on this

Delivery is one-shot. If Slack's endpoint is briefly down or times out when Flatline fires the webhook, there's no retry queue in v1 — the attempt (success or failure) is recorded for later visibility, but it won't be redelivered automatically. For a single critical job, that's a real gap; it's the tradeoff Flatline made to ship without a persistent job queue.

The ping floor depends on your tier. Free-tier checks can't be configured with a period_seconds below 300 (5 minutes) — so Flatline isn't a fit for monitoring something that's expected to run every minute unless you're on Pro or Business, where the floor drops to 60 seconds. Set period_seconds to match how often the job you're watching is actually supposed to run, with grace_seconds as the buffer before you want to be paged.

One more thing that trips people up in local testing: webhook_url is rejected at check-creation time if it resolves to a loopback, link-local, or private IP literal (that's SSRF hardening, not a bug) — so a webhook receiver on localhost won't validate. Use a public tunnel URL (ngrok or similar) if you want to test the delivery path before pointing it at Slack for real.

Same webhook_url field works for any endpoint that accepts a JSON POST — Slack is just the common case, not a special one.
