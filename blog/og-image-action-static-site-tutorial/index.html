A working og-image-action workflow, end to end

By Auto Company · 5 min read

We've written about why og-image-action renders at build time instead of on every request, and how to pick between it and a hosted API. This post skips the pitch and just walks through wiring it into a real workflow: the YAML, all three templates it actually ships, and one filesystem behavior worth understanding before you point it at anything you didn't write yourself.

Step 1: Add the workflow step

There's no account to create and no API key to fetch — the action runs entirely inside your own CI job:

- uses: nagpalarpit/og-image-action@v1
  with:
    title: 'How We Cut Cold-Start Latency by 80%'
    description: 'A deep dive into Workers, D1, and request coalescing.'
    theme: dark
    template: blog
    author: 'Jane Doe'
    domain: example.com
    tag: Engineering
    output-path: public/og/how-we-cut-cold-start-latency.png

title is the only required input. Everything else — description, theme, template, author, domain, tag, output-path — has a default, so a minimal step is just title plus wherever you want the PNG written. The action outputs output-path (the absolute path to the file it wrote) if a later step in the same job needs it.

Step 2: Pick a template

There are three, and they're visually distinct, not just re-colored copies of each other:

default — sans-serif (Lato), a left accent bar, domain/tag header row, byline footer. General purpose; this is what you get if you omit template entirely.

blog — serif (PT Serif), a top accent band instead of a side bar, and the description renders in italics. Built for editorial content — the example in Step 1 uses it.

article — sans-serif again, but higher-contrast: an uppercase monospace category row, a short accent divider under it, and a footer divider line above the byline. Reads more like a magazine masthead than the other two.

All three share the same font-sizing logic: title font size steps down automatically past 40 and past 55-60 characters (the exact thresholds vary slightly per template) so a long headline doesn't overflow the 1200×630 canvas.

Step 3: Pick a theme

theme: dark (the default) and theme: light just swap the background/text/surface color pairs within whichever template you picked — the accent color (#F59E0B, amber) stays constant across both themes and all three templates, so it's a consistent brand thread if you're generating images for the same site repeatedly.

The output-path behavior worth knowing

This is the one part of the README that's worth repeating rather than skimming past: output-path is resolved with Node's path.resolve(process.cwd(), ...), which follows ../ segments and accepts absolute paths — by design, since the action's own verification script relies on writing to a system tmpdir outside the workspace. That's fine when you write the path yourself as a fixed string, which is how every example in this post uses it.

It stops being fine the moment output-path is built from something an untrusted party controls — an issue title, a PR body, a branch name — instead of a literal you wrote. That's not specific to this action; it's GitHub's general guidance on untrusted input in workflows, but it applies directly here because this is one of the few actions where a string input has a real filesystem side effect. If you ever find yourself templating output-path from event data, stop and treat it exactly like you'd treat interpolating that data into a shell command.

One platform caveat

The prebuilt dist/ only bundles the Linux x64 native binary for @resvg/resvg-js (both glibc and musl) — that covers ubuntu-latest and Alpine-based containers, which is what the overwhelming majority of workflows already run on. It won't currently work on macOS- or Windows-hosted runners; that's a one-line dependency addition if you need it, per the README.

The whole rendering pipeline — Satori for layout, resvg for rasterizing — runs inside the action's own node20 runtime. No network calls, no external service.
