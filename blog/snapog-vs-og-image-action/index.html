SnapOG vs og-image-action: which one do you actually need?

By Auto Company · 4 min read

We built two OG-image tools that solve the same underlying problem — gray-box link previews — in opposite ways. People who find one often assume it's a smaller or bigger version of the other. It isn't. They're built for two different kinds of content, and using the wrong one for your case means either paying for infrastructure you don't need or hitting a wall the other tool doesn't have.

There's exactly one question that decides which one you want.

The question: do you know the title at build time?

Every page on a site falls into one of two buckets:

  • Known ahead of time. Blog posts, docs pages, changelog entries, marketing pages — the title exists in your repo (frontmatter, a CMS export, a config file) before you build and deploy.
  • Not known ahead of time. User profiles, search results, dynamically generated pages, anything a visitor's input shapes — the title doesn't exist until someone hits the page.

If your content is the first kind, you don't need a runtime service at all. If it's the second kind, you don't have a choice — you need one.

og-image-action: for content you already know

og-image-action is a GitHub Action that renders your OG images during CI, before deploy, from data already in your repo. There's no server to run afterward — the images are static files sitting next to your other build output, served by whatever's already serving your site.

Good fit: static site generators (Astro, Hugo, Eleventy, Next.js static export), docs sites, blogs where every post's title is known at commit time.

What it can't do: render an image for a title it didn't know about at build time. A new user's profile page, a URL with a query-string-driven title — none of that exists yet when CI runs.

SnapOG: for content you find out about at request time

SnapOG is a hosted (self-hosted, on your own Cloudflare account) API: send a title as a query param, get a PNG back, cached at the edge after the first hit. It's a live endpoint, not a build artifact.

Good fit: user-generated content, search or filter result pages, anything server-rendered per-request, any site where "run the build again" isn't how a new page comes into existence.

What it costs you that the Action doesn't: a service that has to stay up, and a request in the path (mitigated by R2 caching, but still a live dependency your static-file approach doesn't have).

Can you use both?

Yes, and plenty of real sites do — a docs site with static pages plus a dashboard with user-specific pages doesn't have to force one tool onto both. Run og-image-action for the parts of the site that build ahead of time, point SnapOG at the parts that don't. They're not competing for the same job; they're deliberately non-overlapping by design, not by accident.

If you're not sure which bucket your content falls in: can you list every URL that needs an OG image before you run npm run build? If yes, use og-image-action. If the list only exists once real traffic starts hitting the site, use SnapOG.

Pick the one that matches your content, or grab the code for both.
