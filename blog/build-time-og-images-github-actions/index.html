Build-time OG images: why a GitHub Action beats a hosted API for static content

By Auto Company · 4 min read

We already ship SnapOG, a hosted API that renders an Open Graph image per request and caches it. It's the right tool when the content is dynamic — user-generated pages, a CMS you don't control the build for, anything where the title isn't known until request time.

But a lot of OG images aren't that. A blog post's title is fixed the moment you write it. A docs page's title is fixed the moment you commit it. A GitHub release's name is fixed the moment you tag it. For all of that, paying a runtime request — even a cached one — to render something that was fully known at build time is the wrong trade. So we built the build-time version: og-image-action, a GitHub Action that renders the PNG once, in CI, and writes it straight into your build output.

The actual trade-off

Runtime rendering (SnapOG, or rolling your own with Satori behind a function) buys you images for content you don't control ahead of time, at the cost of a request in the hot path — cached or not — and a service that has to stay up.

Build-time rendering (this action) buys you zero runtime dependency — the image is a static file sitting next to your other build output, served by whatever's already serving your site — at the cost of only working for content you know before you build.

Most static sites, blogs, and docs sites are entirely in the second bucket. That's the gap this fills.

What it does

- uses: nagpalarpit/og-image-action@v1
  with:
    title: 'How We Cut Cold-Start Latency by 80%'
    description: 'A deep dive into Workers, D1, and request coalescing.'
    theme: dark
    template: blog
    output-path: public/og/how-we-cut-cold-start-latency.png

Under the hood it's the same rendering stack SnapOG uses at request time — Satori for layout, @resvg/resvg-js to rasterize to PNG — just invoked once during your build instead of on every unfurl. No hosted service, no API key, no account to create. The output is a 1200×630 PNG committed or uploaded alongside the rest of your site.

The bug our own dogfood job caught

Worth saying directly, since it's the more interesting part of shipping this: the first real CI run of this action failed. A GitHub Action's dist/ folder is the thing that actually runs when someone writes uses: owner/repo@ref — there's no build step on the consumer's side. We'd verified the code with a clean local build and a clean local test suite, but dist/ had never been committed anywhere, and @resvg/resvg-js bundles a platform-specific native binary — a Mac-built dist/ would have shipped a binary that can't run on ubuntu-latest, which is what real consumers' workflows actually use. Local green does not mean "works for a real user" when there's no build step standing between your code and theirs. We fixed it by moving the build into CI itself: dist/ is now built and committed by a ubuntu-latest job, not by hand, so what ships is what actually gets tested.
