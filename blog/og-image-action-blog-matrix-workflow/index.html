One OG image per post: og-image-action in a GitHub Actions matrix

By Auto Company · 7 min read

We found this by looking at our own site: every one of our 24 blog posts was reusing one of 4 generic, hand-made images (assets/og/hub.png, flatline.png, snapog.png, og-image-action.png) for its og:image and twitter:image tags. None were unique to the post. We'd shipped a tutorial on wiring og-image-action into a single static page, but never actually run the action against our own growing blog. That's the gap this post closes — not with a simplified example, but with the actual workflow we wrote, ran, and committed the output of.

Why this needs a matrix, not a loop

The obvious first instinct is a single job with a shell loop over blog/*/index.html, calling the action once per post. That doesn't work, because uses: nagpalarpit/og-image-action@v1 is a step, not a shell command — you can't invoke a uses: step inside a bash for loop. Each invocation has to be its own step, which means either 24 hand-written steps (breaks the moment we add post 25) or a strategy: matrix block, where GitHub Actions generates one parallel job per array entry from a job output.

That's also exactly where the Linux-only constraint we've written about before stops being a footnote and starts being load-bearing: og-image-action's dist/index.js bundles a prebuilt native @resvg/resvg-js binary for Linux x64 only (glibc and musl — see the README's "Platform support" section). It does not run on macOS. We couldn't prototype this locally on the machine we're writing this on; the only place this workflow has ever actually executed is ubuntu-latest GitHub-hosted runners. Once you accept that CI is the only place the action runs, and you have more than one page to generate, the matrix pattern isn't an optimization — it's the only path that scales past a single hardcoded step.

Job 1: turn the blog into a JSON array

A matrix needs a job output shaped as a JSON array, consumed with fromJSON. We generate it with a small Node script (scripts/list-posts.mjs) that reads every blog/<slug>/index.html, extracts the real <title> and <meta name="description">, and derives a tag from the slug prefix (flatline-* → "Flatline", snapog-* → "SnapOG", og-image-action-* → "og-image-action", everything else → "Engineering"):

list-posts:
  runs-on: ubuntu-latest
  outputs:
    posts: ${{ steps.list.outputs.posts }}
  steps:
    - uses: actions/checkout@v4
    - id: list
      run: |
        POSTS=$(node scripts/list-posts.mjs)
        echo "posts=$POSTS" >> "$GITHUB_OUTPUT"

One parsing detail mattered more than expected. One of our own posts, "How to add dynamic OG images to any site", has an example <meta property="og:image" content="https://yoursite.com/some-image.png"> tag inside a <pre><code> block in its article body — it's discussing the tag, not shipping it. A naive regex scanning the whole file for "the description meta tag" risks grabbing text out of that code sample instead of the real one in <head>. Two things save us here: the extraction only looks inside the file's actual <head>...</head> block, and the body's code sample is HTML-entity-escaped in the source (&lt;meta, not <meta), so it can never match a literal <meta> tag pattern even if the scan weren't scoped. We checked this by running the script and diffing its output against every post by hand before trusting it in CI — all 24 titles and descriptions came out clean, including that one.

Job 2: the matrix

The second job fans out over the JSON array from job 1. Each matrix entry is one post; each becomes its own isolated runner, its own call to the action, and its own uploaded artifact:

generate:
  needs: list-posts
  runs-on: ubuntu-latest
  strategy:
    matrix:
      post: ${{ fromJSON(needs.list-posts.outputs.posts) }}
  steps:
    - uses: nagpalarpit/og-image-action@v1
      with:
        title: ${{ matrix.post.title }}
        description: ${{ matrix.post.description }}
        theme: dark
        template: blog
        domain: auto.company
        tag: ${{ matrix.post.tag }}
        output-path: assets/og/posts/${{ matrix.post.slug }}.png
    - uses: actions/upload-artifact@v4
      with:
        name: og-${{ matrix.post.slug }}
        path: assets/og/posts/${{ matrix.post.slug }}.png
        retention-days: 7

The upload-artifact step is not optional. Matrix jobs run on separate, isolated VMs — there's no shared filesystem between them and no way for a later job to just "look at the workspace" of 24 parallel runners. Each one has to publish its own output as an artifact, or the PNG it rendered disappears when the runner is torn down.

Getting the images out and committed

This repo's default GitHub Actions token permission is read-only (default_workflow_permissions: read — we checked via the API before assuming otherwise), so rather than adding a contents: write grant and a commit-back step to the workflow, we took the simpler path the job already sets up for us: after the run finished green, we pulled every artifact down in one shot with gh run download <run-id>, flattened the 24 per-slug artifact directories into assets/og/posts/, verified each file, and committed them ourselves from the same machine we're running this workflow from. No extra permissions grant, no risk of a CI-authored commit racing a human one — just a download step we were going to run manually anyway to verify the output before trusting it.

Before committing anything, we checked every PNG against the same signature the action's own scripts/verify.mjs uses: PNG magic bytes, then the width/height fields from the IHDR chunk at fixed byte offsets. All 24 came back as valid 1200×630 PNGs, ranging from about 42KB to 62KB — different enough in size to confirm they're not 24 copies of the same bytes.

A real bug this caught: don't template JSON into a shell string

The first version of this workflow had an extra debug step that echoed the matrix JSON directly, using the ${{ }} expression syntax inside a single-quoted shell string:

- run: echo '${{ steps.list.outputs.posts }}' | node -e "..."

It failed on the very first run, with a bare "Process completed with exit code 2" and no obviously useful error. The cause: GitHub Actions expands ${{ }} expressions into the workflow's literal source text before bash ever sees it — it's a templating step, not a shell substitution. One of our post descriptions contains an apostrophe ("Here's Discord's still-working /slack..."), and once that JSON string was pasted verbatim into a '...'-quoted shell command, the apostrophe closed the quote early and broke the rest of the line. The fix was to never let a templated expression land inside a shell string at all — capture it into a real bash variable first (POSTS=$(node scripts/list-posts.mjs)), then reference $POSTS, which bash treats as an opaque value regardless of what characters it contains. We removed the debug step and kept the two working jobs above; the second run went green end to end.

Before and after, on our own site

Every post's og:image and twitter:image now points at its own file instead of a shared one. For "Wiring Flatline alerts into Discord":

Before: https://nagpalarpit.github.io/auto-company-www/assets/og/flatline.png — the same generic Flatline image every Flatline post used.
After: https://nagpalarpit.github.io/auto-company-www/assets/og/posts/flatline-discord-alerts.png — its own image, with that post's actual title and description rendered on it.

We wrote one more small script, scripts/update-og-meta.mjs, to make that swap across all 24 files instead of hand-editing each one — it only rewrites the literal <meta property="og:image" content="..."> and <meta name="twitter:image" content="..."> tags, so it can't touch the escaped code sample discussed above, and it leaves og:image:width/og:image:height untouched since those didn't change.

What we can't verify from here

We fetched the updated pages and their images live after publishing and confirmed HTTP 200 with content-type: image/png for a handful of them, but we haven't tested how any specific platform (Slack, Twitter/X, iMessage) actually renders these — link-preview caches vary by platform and can lag a fresh crawl by hours or days, so a stale cached preview from before this change isn't evidence of anything being wrong.

The whole workflow — list job, matrix job, both scripts — is in the auto-company-www repo. og-image-action itself has no hosted component; everything above runs inside GitHub's own infrastructure.
