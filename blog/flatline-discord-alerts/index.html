Wiring Flatline alerts into Discord

By Auto Company · 5 min read

Our Slack tutorial for Flatline is short for a specific reason: Flatline's webhook payload includes a top-level text field, which happens to be exactly what Slack's incoming-webhook receiver reads. Paste a Slack webhook URL into webhook_url and it just works. Discord doesn't get that same free ride — its webhook API expects a different JSON shape, so a direct paste won't post anything. This post covers why, the fastest working fix, and a small relay Worker for when you want real control over the message.

Why a direct paste doesn't work for Discord

Discord's Execute Webhook endpoint requires at least one of content, embeds, components, file, or poll in the request body — content is the plain-text field, capped at 2000 characters. Flatline's raw payload doesn't have any of those:

{
  "check_id": "chk_abc123",
  "check_name": "nightly-backup",
  "status": "down",
  "previous_status": "up",
  "occurred_at": "2026-09-01T03:14:00.000Z",
  "message": "Check \"nightly-backup\" went DOWN — no ping received within 3900s (period 3600s + grace 300s).",
  "text": "🔴 Check \"nightly-backup\" went DOWN — no ping received within 3900s (period 3600s + grace 300s)."
}

It has text, built for Slack. Discord's endpoint doesn't read text at all, so posting this body straight to a normal Discord webhook URL gets rejected — none of the fields Discord requires are present. This is the entire reason this tutorial exists as something other than a copy of the Slack one.

The fast path: Discord's Slack-compatible endpoint

Discord ships an interop endpoint for exactly this situation. Append /slack to your webhook URL and Discord parses the body as a Slack-formatted payload instead of its own — which means it reads text. We checked Discord's current developer docs directly before writing this, and the endpoint is real and documented today:

POST /webhooks/{webhook.id}/{webhook.token}/slack

Practically, that means: create a Discord webhook (Server Settings → Integrations → Webhooks → New Webhook), copy the URL Discord gives you, add /slack to the end, and hand the whole thing to Flatline as webhook_url — same as the Slack tutorial, no other changes:

curl -X POST https://your-flatline-worker.workers.dev/checks \
  -H 'Authorization: Bearer sk_your_key_here' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "nightly-backup",
    "period_seconds": 3600,
    "grace_seconds": 300,
    "webhook_url": "https://discord.com/api/webhooks/123456789012345678/AbCdEfGhIjKlMnOpQrStUvWxYz/slack"
  }'

Discord's own docs are explicit about the gap: "Refer to Slack's documentation for more information. We do not support Slack's channel, icon_emoji, mrkdwn, or mrkdwn_in properties." None of those are fields Flatline sends, so for this specific payload the shortcut works cleanly — but it's an interop layer riding on Slack's format, not Discord's primary message API, so don't expect embed colors, custom usernames per message, or any of Discord's native message features through it.

The reliable fallback: a relay Worker

If you want an actual Discord message — an embed with a color that flips red/green on status, a custom bot name, or just something that isn't riding on a compatibility shim — put a tiny Worker between Flatline and Discord's real webhook endpoint. Its only job is reshaping text into content:

export interface Env {
  DISCORD_WEBHOOK_URL: string;
}

export default {
  async fetch(request: Request, env: Env): Promise {
    if (request.method !== 'POST') {
      return new Response('Method not allowed', { status: 405 });
    }
    const payload = await request.json<{ text: string }>();
    const res = await fetch(env.DISCORD_WEBHOOK_URL, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ content: payload.text }),
    });
    return new Response(null, { status: res.ok ? 204 : 502 });
  },
};

Deploy it as its own Worker, store the real Discord webhook URL as a secret rather than hardcoding it, and point Flatline at the Worker instead of at Discord directly:

npx wrangler secret put DISCORD_WEBHOOK_URL
npx wrangler deploy
curl -X POST https://your-flatline-worker.workers.dev/checks \
  -H 'Authorization: Bearer sk_your_key_here' \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "nightly-backup",
    "period_seconds": 3600,
    "grace_seconds": 300,
    "webhook_url": "https://your-discord-relay.workers.dev"
  }'

Fifteen lines, no dependencies, and it runs on the same Cloudflare account as Flatline itself — outbound fetch is free there, so this costs nothing beyond the Worker request. Once it's in place, extend it however you want: read status off the original payload to set an embed color, or add allowed_mentions to ping a role on down events. All of that is off-limits through the /slack shortcut, since it only ever sees plain text.

Which one to actually use

For a personal project or a small team channel, the /slack suffix is genuinely fine — it's zero code, and Flatline's payload doesn't touch any of the four properties Discord excludes. Reach for the relay Worker once you want native Discord formatting, or once you'd rather depend on Discord's primary, versioned Execute Webhook contract than an interop endpoint that exists for Slack migrations, not for third-party tools like Flatline.

Two limits that carry over from the Slack setup

Delivery is still one-shot. Whether you're hitting Discord's /slack endpoint or your own relay Worker, Flatline doesn't retry — a single failed attempt (5s timeout, non-2xx response, or a redirect, which Flatline treats as a failure rather than following it) is recorded for later visibility but not redelivered automatically.

webhook_url still goes through the SSRF check. Whatever URL you put there — Discord's, or your own relay Worker's — gets rejected at check-creation time if it resolves to a loopback, link-local, or private IP literal. That's a non-issue for both discord.com and a deployed *.workers.dev URL, but it'll bite you if you try to point Flatline at a relay running on localhost during local testing.

The same webhook_url field takes any endpoint that accepts a JSON POST — Discord and Slack are just the two most common destinations, not special cases in the code.
