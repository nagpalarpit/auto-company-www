Dynamic OG images in Next.js App Router with SnapOG

By Auto Company · 6 min read

Our last post covered why a static og:image doesn't scale past a handful of pages, and the raw curl-and-meta-tag path to fixing it. This one is narrower: the actual wiring for a Next.js App Router site, using the real generateMetadata API — not a simplified stand-in — plus the equivalent for Astro and Hugo at the end.

The shape Next.js expects

Next's openGraph.images field isn't a bare URL string (though it accepts one) — the documented, complete form is a list of objects with url, width, height, and an optional alt:

openGraph: {
  images: [
    {
      url: 'https://nextjs.org/og.png', // must be an absolute URL
      width: 800,
      height: 600,
    },
  ],
}

Two things that matter for SnapOG specifically: the URL must be absolute (SnapOG's endpoint always is — it's a full Worker URL), and Next.js will happily forward query strings as part of that URL. That's the whole integration surface — build the query string per-page, hand it to openGraph.images.

Static route: layout.tsx or page.tsx

If the title is known at build time, skip generateMetadata entirely and export a plain metadata object:

import type { Metadata } from 'next'

const ogImage = 'https://your-worker.your-subdomain.workers.dev/og?' +
  new URLSearchParams({
    title: 'Pricing',
    key: process.env.SNAPOG_KEY!,
  })

export const metadata: Metadata = {
  title: 'Pricing',
  openGraph: {
    images: [{ url: ogImage, width: 1200, height: 630 }],
  },
}

Dynamic route: generateMetadata

For a blog post, product page, or anything keyed off route params, use generateMetadata. This is the version that actually earns its keep — every post gets a real, per-post image with no manual export step:

// app/blog/[slug]/page.tsx
import type { Metadata } from 'next'

const SNAPOG_URL = 'https://your-worker.your-subdomain.workers.dev'

type Props = { params: Promise<{ slug: string }> }

export async function generateMetadata({ params }: Props): Promise<Metadata> {
  const { slug } = await params
  const post = await getPost(slug) // however you already fetch post data

  const ogImage = `${SNAPOG_URL}/og?${new URLSearchParams({
    title: post.title,
    description: post.excerpt,
    tag: post.category,
    template: 'blog',
    key: process.env.SNAPOG_KEY!,
  })}`

  return {
    title: post.title,
    description: post.excerpt,
    openGraph: {
      title: post.title,
      description: post.excerpt,
      images: [{ url: ogImage, width: 1200, height: 630 }],
    },
    twitter: {
      card: 'summary_large_image',
      images: [ogImage],
    },
  }
}

export default async function Page({ params }: Props) {
  const { slug } = await params
  const post = await getPost(slug)
  return <article>{/* ... */}</article>
}

Two Next.js-specific details worth calling out:

  • URLSearchParams handles the encoding for you — titles with &, spaces, or unicode won't break the query string. Don't hand-build it with template literals.
  • If a parent layout already sets an openGraph.images default (e.g. a site-wide fallback image), a child route's generateMetadata replaces it, it doesn't merge. If you want to extend rather than replace, read (await parent).openGraph?.images and spread it in — that's documented behavior, not a SnapOG quirk.

One more thing worth being upfront about: the key ends up in the rendered page's HTML, in plain view, because og:image is a public meta tag by definition — any platform unfurling the link has to be able to fetch it with no auth. That's true of SnapOG's key exactly the same way it's true of any API key used as a query param on a public asset URL. It's fine for what the key is for (rate-limited PNG generation on your own instance), but don't reuse that same key for anything that isn't meant to be public — the /register endpoint is free to call again if you want a dedicated one.

Pages Router, briefly

If you're still on the Pages Router, there's no generateMetadata — build the same URL and drop it into next/head inside getStaticProps/getServerSideProps instead:

import Head from 'next/head'

export default function Post({ post, ogImage }) {
  return (
    <>
      <Head>
        <meta property="og:image" content={ogImage} />
        <meta property="og:image:width" content="1200" />
        <meta property="og:image:height" content="630" />
      </Head>
      {/* ... */}
    </>
  )
}

Astro

Astro doesn't have a metadata API of its own — you build the URL in frontmatter and drop it straight into the layout's <head>:

---
// src/layouts/BlogPost.astro
interface Props {
  title: string;
  description: string;
}
const { title, description } = Astro.props;
const ogImage = `https://your-worker.workers.dev/og?${new URLSearchParams({
  title,
  description,
  key: import.meta.env.SNAPOG_KEY,
  template: 'blog',
})}`;
---
<head>
  <meta property="og:image" content={ogImage} />
  <meta property="og:image:width" content="1200" />
  <meta property="og:image:height" content="630" />
  <meta name="twitter:card" content="summary_large_image" />
  <meta name="twitter:image" content={ogImage} />
</head>

Same pattern as Next's Pages Router: no special API to learn, it's a plain template variable.

Hugo

Hugo's template functions can build the same URL server-side at build time, in a head.html partial. The one gotcha: Hugo only exposes environment variables to templates if they're prefixed HUGO_ — plain SNAPOG_KEY won't be visible to getenv, it has to be set as HUGO_SNAPOG_KEY in the build environment.

{{ $ogImage := printf "https://your-worker.workers.dev/og?title=%s&key=%s&template=blog"
    (.Title | urlquery) (getenv "HUGO_SNAPOG_KEY") }}
<meta property="og:image" content="{{ $ogImage }}">
<meta property="og:image:width" content="1200">
<meta property="og:image:height" content="630">

urlquery is doing the same job URLSearchParams does in the JS examples — encode the title before it hits the query string, don't concatenate it raw.

All three of these hit the same endpoint — deploy it once, wire it into whatever renders your pages.
