SnapOG vs Vercel OG: same rendering engine, different place to run it

By Auto Company · 5 min read

@vercel/og is the first thing most developers reach for when they need a dynamic Open Graph image, because it ships inside Next.js and there's nothing to install. It's also the tool people compare every OG-image alternative against, including SnapOG. So it's worth being precise about what actually differs, because it isn't what you'd guess.

SnapOG renders images with workers-og, a Cloudflare Workers-compatible library built on Satori. @vercel/og is built on Satori too — Vercel wrote Satori. Both pipelines take a JSX-like element tree, lay it out with Satori's flexbox-only CSS engine, and rasterize the resulting SVG to a PNG (workers-og and @vercel/og both hand that last step to a WASM build of Resvg). Pixel-for-pixel, there's no "better renderer" argument to make here — it's the same core technology on both sides. The honest difference is architecture: who runs the code, and where the resulting image lives afterward.

@vercel/og: a library you import and host yourself

Per Vercel's current docs, OG image generation is a ImageResponse constructor from the @vercel/og package (bundled automatically as next/og in the Next.js App Router — no separate install needed there). You write the route yourself:

  • Create app/api/og/route.tsx (App Router) or pages/api/og.tsx (Pages Router), return new ImageResponse(<div>...</div>, { width: 1200, height: 630 }).
  • Runs as a Vercel Function on the Node.js runtime (Vercel's docs note a caveat: Pages Router + Node.js runtime doesn't support the return new Response(...) syntax @vercel/og relies on — App Router and Edge-runtime Pages Router are fully supported).
  • By default it sets content-type: image/png and cache-control: public, immutable, no-transform, max-age=31536000 on the response, so Vercel's own CDN can cache a hit at the edge — but that caching lives inside your Vercel deployment. There's no separate, portable image store; redeploy or move platforms and the cache resets with it.
  • It only outputs a ReactElement, so you're writing JSX (or using Vercel's experimental Tailwind support) for every layout variant — SnapOG's template/theme params don't have an equivalent; you build your own.
  • Cost isn't a separate line item — it rides on your existing Vercel plan's Function invocations and bandwidth. We didn't find current per-plan numbers worth quoting here since they change independently of this comparison; the honest framing is "adds to usage you're already paying for," not "free."

Satori itself is platform-agnostic — pairing it with @resvg/resvg-js outside Vercel is a documented pattern (and there are community ports, like m5r/og, that reimplement the same API for plain Node.js). But the @vercel/og package itself is written for Vercel's Function runtime, and using it means the render route lives inside your app's deployment, in your app's language (JSX/React), on your platform's infra.

SnapOG: a hosted endpoint you call from anything

SnapOG (open source, MIT) is the opposite shape: GET /og?title=...&key=... with optional description, domain, author, tag, template (default/blog/article), and theme (dark/light) params, returning a 1200×630 PNG. No JSX, no framework requirement, no route to write — a <meta property="og:image"> tag or a plain curl call is the entire integration, from any stack: Rails, PHP, a static Hugo site, or a Next.js app that just doesn't want to own this code.

It's built the same way: Cloudflare Workers + Hono, rendering through workers-og (Satori-based, same pipeline shape as @vercel/og). The difference is what happens after render. SnapOG hashes the sorted request params (SHA-256) into a cache key and stores the PNG in a Cloudflare R2 bucket at og/<hash>.png — a persistent, content-addressed object store that isn't tied to any one deployment, plus a daily scheduled sweep that reaps entries untouched for 30+ days so the bucket doesn't grow unbounded. A repeat request for the same params is an R2 read, not a re-render, and the response tells you which happened via an X-Cache: HIT|MISS header (plus X-SnapOG-Tier). Usage is tracked and rate-limited per API key in a D1 database.

Like the comparison posts before this one: SnapOG is open source and designed to be deployed to your own Cloudflare account, so it's free to run at Cloudflare's free-tier limits — there's no separate SaaS bill unless you choose to enable the built-in Pro ($19/mo, 10,000 images) or Business ($49/mo, 100,000 images) tiers, which exist in the code as a Stripe-gated upgrade path. The free tier (100 images/month) watermarks output; paid tiers don't.

The actual trade-off

  • Pick @vercel/og if you're already shipping a Next.js app on Vercel and want the render code living in your own repo, in your own language, with full control over layout, fonts, and emoji sets — and you're fine with the cache living and dying with your deployment.
  • Pick SnapOG if you want "title in, image out" without writing a render route at all, you're not on Next.js/Vercel, or you want a cache that persists as a standalone artifact independent of any single app's deploy lifecycle.

Neither one wins on image quality — they're both Satori under different hoods. The question is only ever "do I want to own this route, or call someone else's."

Can you use both?

Yes, and it's a reasonable split: use @vercel/og for pages that are part of the Next.js app itself (dashboards, per-user pages you already render server-side), and point SnapOG at everything outside that boundary — a marketing site on a different stack, a docs subdomain, anything that shouldn't need a Vercel deployment just to get a share image.
